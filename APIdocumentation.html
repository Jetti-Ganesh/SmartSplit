App Overview

What is SmartSplit and what does it do?

SmartSplit is a full-stack expense-splitting app — like Splitwise, but built by you. Users create groups, add expenses, split them equally or by exact amounts, and settle debts. There's also a full analytics dashboard, profile management, and notifications.

Architecture

How frontend and backend talk to each other
PROJECT STRUCTURE
📁 Client/
src/ App.jsx ← Routes defined here main.jsx ← Redux store + React mount pages/ ← One file per screen components/ ← Reusable UI pieces services/ ← API calls + Redux slices store/ ← Redux store config styles/ ← Per-component CSS files context/ ← NotificationContext utils/ ← Helper functions
📁 Server/
index.js ← Start server + DB connect app.js ← Express + all middleware routes/ ← Route definitions controllers/ ← Business logic models/ ← Mongoose schemas middlewares/ ← auth.js (JWT protect) utils/ ← mailer.js db/ ← db.js (MongoDB connect)
How they connect: The React frontend runs on localhost:5173. The Express backend runs on localhost:5000. All API calls go to /api/... with a Bearer token in the Authorization header. In production, Express serves the React build directly from Client/dist.
Session + JWT: SmartSplit uses BOTH session (for OTP storage during signup/forgot-password flow) AND JWT (for protecting all API routes after login). The session is stored in MongoDB via connect-mongo. JWT is signed with JWT_SECRET and expires in 7 days.

Sign Up Flow

How a new user creates an account
The key rule: OTP must be verified BEFORE account creation. The session stores otpVerified=true after OTP is confirmed. If this flag isn't set, signup is rejected.
1
User opens Sign Up page
User chooses to sign up via email or phone number. This sets the signupMethod.
2
Send OTP — POST /api/send-otp
Frontend sends email or phone. Server generates a 6-digit OTP using crypto.randomInt(100000, 999999). Stores OTP in both a Map (with TTL) and in the session. Sends via Nodemailer (email) or Fast2SMS → Textbelt fallback (phone).
3
Verify OTP — POST /api/verify-otp
User enters the OTP. Server checks the otpStore Map first (preferred), then session fallback. Checks expiry. On success, sets req.session.otpVerified = true.
4
Create Account — POST /api/signUp
Only proceeds if req.session.otpVerified === true. Checks for duplicate email/phone. Hashes password with bcrypt (10 salt rounds). Saves user. Issues JWT (7 days). Sends welcome email. Clears OTP session.
5
Redirect to Dashboard
JWT token stored in Redux authSlice. User is now logged in. Redirect to /dashboard.

Request Body
// Send one of these — not both { "email": "ganesh@example.com" } // OR { "phone": "9876543210" }
Success Response (200)
{ "message": "OTP sent to your email.", "devOtp": "482910" // returned in dev mode for phone }

Login Flow

Email or phone + password → JWT token
1
User submits login form
Provides email or phone + password. POST /api/login.
2
Server finds user
If email: finds by email. If phone: strips spaces, +91 prefix, finds by 10-digit number. User not found → 401.
3
Password check
bcrypt.compare(password, user.password). Wrong password → 401. Match → proceed.
4
JWT issued + notification added
jwt.sign({userId}, JWT_SECRET, {expiresIn: '7d'}). Also pushes a "Logged in successfully" notification to the user's notifications array. Returns token + user object.
POST /api/login Login with email or phone
Request Body (email login)
{ "email": "ganesh@example.com", "password": "mySecret123" }
Request Body (phone login)
{ "phone": "9876543210", "password": "mySecret123" }
Success Response (200)
{ "message": "Login successful.", "token": "eyJhbGci...", "user": { "id": "64abc...", "name": "Ganesh", "email": "ganesh@example.com", "isEmailVerified": true } }

Google Auth

One-click login / signup with Google
How it works: The frontend uses the Google SDK to get the user's Google profile (name, email, googleId). It then sends that to your backend. If the email already exists in DB, it logs them in. If not, it auto-creates a new account. No OTP step needed.
POST /api/google-auth Sign in or sign up with Google
Request Body
{ "name": "Ganesh Jetti", "email": "ganesh@gmail.com", "googleId": "108237491823749182" }
Success Response (200)
{ "message": "Google auth successful.", "token": "eyJhbGci...", "user": { "id": "...", "name": "Ganesh" } }
Note: Google users cannot log in with email+password later because their password is stored as google_<googleId> — not a real hash.

Forgot Password

3-step OTP-based password reset
1
Request OTP — POST /api/forgot-password
User provides email or phone. Server checks if account exists. Sends OTP via email (Nodemailer) or console (phone dev mode). Stores in session.
2
Verify OTP — POST /api/verify-reset-otp
User submits the OTP. Server matches session OTP. Sets req.session.resetVerified = true.
3
Set New Password — POST /api/reset-password
Requires resetVerified === true in session. Validates new password (min 6 chars, must match confirm). bcrypt hashes + saves. Clears reset session vars.

Groups

Create, join, manage expense groups
Groups are the core unit of SmartSplit. Every expense belongs to a group. When you create a group, you automatically become its admin. You can then add members by email, or share a 6-character invite code for them to join themselves.
1
Create Group
Admin provides name, icon (emoji), optional description. A unique inviteCode is auto-generated by a Mongoose pre-save hook using Math.random().toString(36).substring(2,8).toUpperCase(). Creator is added as role: 'admin'.
2
Add Member by Email
Admin sends POST /api/add-member/:groupId with the member's email. Server finds user by email, checks if not already a member, pushes to group.members. Sends the new member an in-app notification.
3
Join by Invite Code
Anyone with the code sends POST /api/join-group with the code. Server finds group by inviteCode (case-insensitive). Adds user as role: 'member'. Sends welcome notification.
4
Get All Groups with Balances
GET /api/getgroups fetches all groups where user is a member. For each group, it calculates the user's net balance by scanning all expenses: what others owe you minus what you owe others. Returns userBalance: {owed, owing, net} for each group.

Expenses

Add and view expenses inside a group
Split types supported: equal (divide equally among selected members) and exact (you specify each person's exact share). The server validates that splitDetails always sum to the total amount (±₹0.10 tolerance for float errors).
1
User opens a group → clicks "Add Expense"
User fills: description, amount, category, who paid (paidBy), split type, members to split between.
2
Server validates membership
Checks that the group exists and the current user is a member. Non-members get a 403.
3
Split calculation
Equal split: Converts to "paisa" (×100) to avoid float errors. Divides total among members. Adds remainder to first person.

Exact split: Uses the splitDetails you provide. Validates sum is within ±₹0.10 of total.
4
Expense saved, returned populated
Mongoose pre-save hook also validates split sum. Response includes populated paidBy.name and splitDetails[].userId.name.
POST /api/create-expense Add an expense to a group 🔐
Equal Split Example
{ "groupId": "64xyz...", "description": "Dinner at Hyderabad House", "amount": 1200, "category": "Food", "paidBy": "64abc...", // userId of who paid "splitType": "equal", "selectedMembers": ["64abc...", "64def...", "64ghi..."] }
Exact Split Example
{ "groupId": "64xyz...", "description": "Hotel bill", "amount": 3000, "splitType": "exact", "splitDetails": [ { "userId": "64abc...", "amount": 2000 }, { "userId": "64def...", "amount": 1000 } ] }
Success Response (201)
{ "success": true, "data": { "_id": "64exp...", "description": "Dinner at Hyderabad House", "amount": 1200, "paidBy": { "name": "Ganesh" }, "splitDetails": [ { "userId": { "name": "Ganesh" }, "amount": 400 }, { "userId": { "name": "Ravi" }, "amount": 400 }, { "userId": { "name": "Suresh" }, "amount": 400 } ] } }

Returns all expenses sorted by date (newest first). Only group members can view. Each expense is populated with payer and participant names.

Settle Up

Calculate balances, record payments, simplify debts
How balances are calculated: For every expense, each splitDetails entry means that person owes the payer their share. The server builds a pairwise "who owes whom" map, then applies all recorded settlements to reduce those debts. Net result = current outstanding balances.
1
View balances — GET /api/settlements/:groupId/balances
Scans all expenses in the group. Builds a pairwise debt map. Applies all recorded settlements to reduce debts. Returns final outstanding debts + settlement history.
2
Simplify debts — GET /api/settlements/:groupId/simplify
Runs the debt simplification algorithm: calculates each person's net balance, separates creditors and debtors, matches them greedily to minimize the number of transactions needed to settle everything.
3
Record payment — POST /api/settlements
When someone pays, this records the settlement. Security check: you must be either the payer (from) or receiver (to). Future balance calculations automatically subtract this payment from the outstanding debt.
GET /api/settlements/:groupId/balances Who owes whom in a group 🔐
Response
{ "success": true, "data": { "balances": [ { "from": "64def...", "fromName": "Ravi", "to": "64abc...", "toName": "Ganesh", "amount": 800 } // Ravi owes Ganesh ₹800 ], "settlements": [...], // Last 10 payments "group": { "name": "Goa Trip 2025" } } }
POST /api/settlements Record a payment 🔐
Request Body
{ "groupId": "64xyz...", "from": "64def...", // who paid "to": "64abc...", // who received "amount": 800, "method": "upi", "notes": "PhonePe transfer" }
GET /api/settlements/:groupId/simplify Simplify all debts 🔐
Runs the greedy simplification algorithm. Example: A→B ₹100, B→C ₹100 simplifies to A→C ₹100 (one transfer instead of two).
Response
{ "data": { "current": [...original debts...], "simplified": [...minimized debts...], "savings": 2 // saved 2 transactions } }

Analytics

Spending insights, trends, and category breakdown
All analytics are based on the user's share — not the full expense amount. So if a ₹900 dinner was split 3 ways, your analytics show ₹300, not ₹900. This is done via MongoDB aggregation pipeline filtering on splitDetails.userId.
1
Period filter
Query param ?period=7d or month (default) or custom (with startDate + endDate). All 8 analytics data points use this date range.
2
8 data points computed in one call
① Total Spent — sum of your shares.
② Total Owed to You — you paid, others owe you.
③ Total You Owe — others paid, you owe.
④ Category Breakdown — your share per category with % + color + emoji.
⑤ Spending Trend — per-day chart (your spend vs group average).
⑥ Expense List — last 50 expenses you're in.
⑦ Group Breakdown — spend per group.
⑧ Smart Insight — auto-generated text message based on your data.
GET /api/analytics?period=month Full analytics dashboard data 🔐

endDateISO dateOnly if period=custom

Theme System

Dark / Light mode via CSS custom properties
Implementation: CSS custom properties (variables) are defined in index.css for both :root (light) and [data-theme="dark"]. React's themeSlice stores the preference. The ThemeToggle component dispatches the toggle action and applies data-theme attribute to document.documentElement.
/* index.css — CSS variables approach */ :root { --bg-primary: #ffffff; --text-primary: #1a1a2e; --accent: #6c63ff; } [data-theme="dark"] { --bg-primary: #0d0f14; --text-primary: #e8eaf0; --accent: #a89cff; }
// themeSlice.js — Redux slice const themeSlice = createSlice({ name: 'theme', initialState: { theme: 'light' }, reducers: { toggleTheme: (state) => { state.theme = state.theme === 'light' ? 'dark' : 'light'; } } });

Auth Middleware

How every protected route is guarded
Every route marked 🔐 in this doc passes through the protect middleware in middlewares/auth.js.
1
Extract token from header
Looks for Authorization: Bearer <token>. If missing → 401 "Not authorized".
2
Verify JWT
jwt.verify(token, process.env.JWT_SECRET). Invalid token → 401. Expired → 401 with "Token expired" message.
3
Find user in DB
User.findById(decoded.userId). If user deleted/not found → 401. Otherwise attaches full user object to req.user.
4
Pass control to controller
next() is called. Controller now has req.user._id, req.user.name, etc. ready to use.
// Example: How frontend attaches token to every request fetch('/api/getgroups', { headers: { 'Authorization': `Bearer ${token}`, // token from Redux store 'Content-Type': 'application/json' } });

Email (Mailer)

Nodemailer + Gmail SMTP
3 email types are sent:
🎉
Welcome Email
Sent after successful email signup. Contains user's name. Triggered in signUpUser controller.
🔢
OTP Email
6-digit OTP for signup verification. Valid for 5 minutes (in-memory TTL). Sent via mailer.sendOTP().
🔑
Password Reset OTP
Sent during forgot-password flow. HTML email with styled OTP. Valid for 10 minutes (session-based).
Phone OTP: Attempts Fast2SMS first (your active key is hardcoded — move to env!). Falls back to Textbelt free tier. If both fail, logs OTP to server console and returns it in the response as devOtp.
